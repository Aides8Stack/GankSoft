## 1. 当前源码中已核实的具体缺口

1. `src/unified/UnifiedWorkspace.vue` 将 `rows/cursor/query/mode/selection/scroll/sort` 全部存入 `lastLists`；`cards()` 直接还原 `rows`，`back()` 只在少数条件下读取 `loadCards`。复盘成功没有统一通知父工作台失效旧列表。**这能够解释“关闭重启软件后更新、未重启仍旧”的症状**；实际 DB 同事务仍须独立核验。
2. `src/unified/UnifiedAnalytics.vue` 的 `load()` 仅由初次挂载、`deckId` 变化、手动日期操作调用；`knowledgeRows` 是保留的读取结果，没有统一订阅后端变更。
3. `src/unified/UnifiedDeckOverview.vue` 的 `load()` 仅 watch `deckId`，同时查询 `workspace.dashboard` 与 `workspace.analytics`，未检查两次读取的修订是否相同。
4. `electron/protocol/gateway.ts` 响应信封已有 `dataEpoch` 和 `dataRevision`；`shared/protocol/client.ts` 在解包后只返回 `Output<M>`，业务页面没有可供一致性判断的 revision。**优先扩展既有客户端的元信息回传，不新建另一个 IPC 通道。**
5. `src/review/UnifiedReviewForm.vue` 在 submit 后读回本会话，但父级没有接收“可信复盘提交”消息，因此卡片列表/概览/分析未同步失效。提交竞态、仅练习路径等另按 #30/#31 同轮修复。

## 2. 唯一写入成功标准

- **正式写入成功** = 已核验的数据库事务成功 + 请求幂等回执（含同一 `dataEpoch` 与单调 `dataRevision`）。复盘评分必须一事务写 `learning_review_events` + `schedule_events` + `scheduling`，否则整体失败，不能显示已保存。
- 不允许先更新 UI 计数并假装成功；后端拒绝、校验失败或回执未知时保留当前输入/评分，不发送“写入成功”事件。
- 请求的结果未知（`COMMIT_UNKNOWN` / `OPERATION_UNKNOWN` / 传输中断）时，仅用**原 requestId** 查询 `operation.status`；查明确认为 committed 才发布成功变更，同一 requestId 只发布一次；若未知可安全重读，但不能误报成功或再次生成学习事件。
- 业务事务与修订/回执的时间窗口应在正式实施中核验并尽可能收敛到同一个原子完成点。若现有网关完成顺序不能严格满足，必须测试并解决“DB 已写但修订还未提升”的可见性竞态；不得仅靠调用顺序假设一致。
- 已提交成功但刷新读取失败时，必须清楚区分“**保存成功，页面数据尚未刷新**”，隐藏或遮蔽过期统计并提供“重新读取”；在导航/激活时自动重试。绝不能把旧值标成新值。

## 3. 统一元信息与轻量失效机制

- 复用现有信封字段 `{dataEpoch, dataRevision}`。在 `shared/protocol/client.ts` 与 `src/services.ts` 新增**不破坏原业务返回值**的元信息读取/订阅：从所有可信 write receipt 及 query reply 获取 revision；命令完成后发布带 `{epoch,revision,requestId,deckId,domains}` 的轻量“数据已更改”信号。
- 每个业务页面有当前读取的 `epoch + revision + filterHash + requestSequence`。**只有同 epoch、符合当前筛选、修订不早于已确认提交修订、且属于最新请求**的查询结果可以覆盖当前 UI。旧异步请求即使最后到达，也必须丢弃。
- 不增加持久化的缓存总表或第二套业务快照。可有组件生命周期内的只读数据，但一旦收到匹配域的写入事件即标记 stale，重新调用原 API。
- 进入页面、从其他主页面返回、切换卡片集、窗口重新获得焦点、窗口重新显示、设置恢复/导入完成时，使用现有便宜的协议查询/能力握手核对 `dataEpoch,dataRevision`；不一致重新读取。**无需周期性全库轮询**。
- `dataEpoch` 变化（恢复备份/迁移）视为全部缓存失效，清理卡片/知识点/分析/复盘会话引用、分页游标与队列过期标识，重新握手并读取，防止旧数据库身份混入。
- 日期相关指标如“今天待复盘、逾期”即使没写入也会跨日变化；读模型缓存键应含**学习时区与 studyDay**，跨学习日、时区调整或重新激活时重新计算。

## 4. 页面数据与 UI 上下文严格分离

**允许保留的只有交互上下文**：`deckId`、查询词、卡片模式、排序、筛选、选中项 ID、分页位置、滚动位置、来源页面。可以尽量恢复滚动/焦点，但不得利用其携带旧卡片成绩。

**不允许跨变更长期保留作为“最新事实”**：卡片列表 rows、复盘次数、最近评分、到期状态、知识点掌握度、学习分析聚合、复盘队列结算汇总及历史条目、AI 导出的待执行前后状态。

- `lastLists` 优先调整为仅保存 UI 上下文；重返列表必须重新调用 `card.listSummary`。若保留快照作为快速首屏，必须先比对 revision，过期时仅显示载入态，不准让旧成绩短暂冒充当前。
- `workspace.dashboard` 与 `workspace.analytics` 两路并发读，只有两者的 `epoch,revison` 一致才作为同一概览批次显示；否则按最新修订重新读，避免同屏“9次复盘/8次分析”的矛盾。
- 分页结果/知识树分批读取必须绑定 `epoch,revision,filterHash`；当 `DATA_REVISION_CHANGED` 或知识关联/树修订变化，丢弃旧游标及已混合页，重新读取第一页或可恢复的定位页，禁止把新旧分页混在一起。
- 正在编辑的**未提交表单内容**不受统计刷新覆盖；只读统计主动刷新，但若用户同时修改同张卡，显示版本冲突并保护内存草稿。暂停的复盘不会因为刷新自动恢复计时。

## 5. 变更来源 → 必须自动失效的读模型

| 成功写入来源 | 必须即时失效/刷新 |
| --- | --- |
| `learning.review.submit`、完成队列 | 当前卡片列表/详情、卡片集概览、学习分析两个维度、关联知识点掌握、复盘队列与历史、学习队列预览、学习总览相关计数 |
| 卡片发布/编辑/软删/恢复、批量导入 | 卡片列表、卡片集概览、目录数量、学习/知识关联统计、知识点读模型、AI 分析导出快照有效性 |
| 知识点新增/合并/删除/恢复、卡片知识关联变化 | 知识图谱/大纲、知识选择器、卡片与知识点聚合、图谱影响的筛选结果、AI 快照 |
| 调度参数保存、单卡覆盖、重新计算、AI 调度动作 apply/undo | 到期时间/待复盘状态、卡片列表、学习总览、卡片集概览、学习分析当前状态、学习队列预览、AI 后续导出/预览 |
| Markdown/ZIP 导入改变题目或树 | 相关卡片、知识点、统计与目录，按实际影响域刷新 |
| Prompt 内容编辑保存 | Prompt 及下次导出文件，**无需无意义地重算学习得分和全部卡片列表** |
| 备份恢复、数据库目录迁移、epoch 变化 | **全部**业务读模型、活动引用与分页游标；重新绑定当前数据库身份 |

内部可用轻量 `domains` 标签缩小主动刷新范围；若只知道全局 revision 变化但来源未知，则采用保守重读，不留旧结果。

## 6. AI 调度调整与长时间分析的特有一致性

- ZIP 导出从**固定数据库快照**生成 `exportId,snapshotId,dataEpoch,dataRevision`，manifest 对各卡 `contentVersionId,cycleId,scheduleHash` 和知识树/配置版本记录校验摘要，文件按卡分片；生成过程中数据变化时使用一致快照或中止重导，不能导出前后矛盾的拼接包。
- AI 返回 ZIP 只作为**建议**。导入“解析”时逐项对照最新 DB 和源快照，旧版本/被删除/已复盘的新排期/已更改知识关系等标记冲突，不执行；在应用前**再次**读最新 revision 并执行事务级比较，不允许预览时有效、执行时无核验。
- 多批返回建议的相同卡片目标去重与跨批冲突检查；任何单次已选动作集执行时发现冲突则整体终止，请用户重新解析，不暗中部分应用。已明确允许的独立无冲突批次可在新的用户确认后单独应用。
- AI 成功应用/撤销后，与人工调度调整使用**同一失效事件与读模型**；“解析记录”仅持久化实际变更摘要，解析预览不计为已执行也不改变统计。

## 7. 定向验收门槛（正式实现时验证，当前均 NOT_RUN）

1. 一张卡 `保存评分` → DB 三表记录一致 → 不重启切至“所有卡片”立刻看到复盘次数、最近分数、到期状态变化；从详情、概览、学习分析、知识点统计均可读取新值。
2. 六卡队列最后一张保存后自动结算归档，刷新“复盘历史/结算/概览/分析”一致，重启读回与未重启一致。
3. 返回卡片列表，搜索/筛选/排序与滚动尽量保留，但卡片的实际数据**必须是新查询**；禁止旧 `lastLists.rows` 覆盖。
4. 连续两次快速写入 + 延迟旧查询回包：旧 revision 不得覆盖新结果；并发 dashboard/analytics 必须展示同一版本的统计。
5. 日期切换、知识点子树变更、分页至下一页期间写入：没有新旧数据混页，旧 cursor 安全失效。
6. AI 方案解析后用户继续复盘 → AI 再点“应用”应检测冲突，不覆盖更新后的 FSRS；成功 apply/undo 后卡片/知识点/调度显示同步。
7. SQLite 写失败、回执未知、读刷新失败、恢复备份 epoch 改变：绝不显示虚假“全部已更新”；保留本地未提交内容、允许安全恢复。
8. 失焦/切页/恢复窗口和跨学习日：有新修订或时间边界时自动重新读取，无须退出软件。
9. Linux Electron GUI → IPC → SQLite → 页面切换 → 新进程重启一致性；Windows 10/11 及 125% DPI 必须单独验收，未测 NOT_RUN。
10. 性能：只刷新受影响的页面与 domain，不因每一次 Prompt 修改重算全部知识点；无无限重试/频繁全库轮询。
