# GankSoft v0.7.7 — 模块化与复杂度控制硬约束

> 用户 2026-10-31 明确要求：**“确保所有改进不会增加软件的复杂度，而是通过 API、模块化保证软件的结构。”** 此要求**覆盖 B1–B5 的所有后续生产开发**，不是单独一个 Vue 界面的小修饰。
>
> 所有新功能都有必要的业务复杂度；本文件控制的是**不必要的重复代码、并行状态机、跨层耦合、额外协议/数据库结构与回归成本**。不能靠新增大量抽象层假称“模块化”。

## 1. 必须遵守的架构原则

1. **优先复用，禁止平行造轮子。** 已有的卡片、草稿、知识树、目录、Markdown、Electron IPC API 可以满足需求时，先补复用/入口，不允许为了新按钮再造独立 service、表或 store。
2. **按职责模块化，不按页面复制。** UI 展示、选择器/编辑器交互状态、业务服务、持久化事务必须分层；相同业务行为只有一份核心逻辑，不允许各页面复制三套“差不多”的状态机。
3. **前端选择 API 不等于写库 API。** 模态框、知识点搜索/选择、目录定位与暂存等均属于前端受控逻辑；只有明确用户动作才走现有业务 IPC、事务与回执，不把选中状态和永久写入耦合。
4. **保持 Schema606 单一生产数据模型。** 不回退旧 legacy 表；不建立第二套卡片/知识点真相源。完整卡片集 ZIP 导出和逐节点 Markdown 导出确需新协议时，只扩展**必要的受控领域接口**，不增加“万能导入导出层”。
5. **稳定视觉接口。** 以 `OPEN-ME-v3.7.html` 和已确认的 `docs/v077/prototypes/` Vue 原型为 UI 合同；保留左侧窄栏、密集小图标、悬停提示，不为实现一个新动作造一整页、浮层或平行导航。原型模拟数据不得泄漏到生产。
6. **接口简单而明确。** 少量稳定参数（例如 `deckId`、`initialSelectedIds`、`purpose`）+ 单一确认回执。禁止多个模块同时保留可写“已选 ID/保存成功/当前路由”副本而没有唯一真相源；删除已失效代码前核对运行可达性与兼容性。
7. **明确依赖和负面行为。** 选择器仅选中并返回、调用页面才保存/应用；导出预览不能暗自发布；删除文件夹默认非级联；改变图谱焦点不能暗中勾选；正常校验失败不能写数据库。
8. **小步交付。** 仍按 `IMPLEMENTATION-WORKPLAN.md` 的 B1–B5，每批最多3检查点，不并发修改 `UnifiedWorkspace.vue` 等热点文件；只新增真正必要的测试，不重跑250条无关旧合同。

## P0 补充：学习提交记录与调度必须是同一原子合同（2026-10-31）

用户最新决策：**取消「仅练习、不更新排期」作为新正式学习的选择或 API 绕过。** 所有实际评分并确认保存的学习，统一由**现有** `learning.review.submit` 完成 `learning_review_events`、`schedule_events` 和 `scheduling` 同事务落库；异常时保留作答并阻止虚假成功。记录与调度状态的读取刷新也属同一用户业务闭环。

不能为此再引入练习版 API、学习完成旁路、影子事件表、新调度引擎、额外持久 Store 或另一个 IPC 方法；只复用既有复盘会话、SQLite 事务、`advanceSchedule`、幂等回执和按需数据刷新。**移除绕过必须同时涉及 UI 与服务端新写入合同，不得只隐藏复选框**。已有历史 practice 记录保持原样，读取兼容与新写入有效性明确区分。与 [#30](https://github.com/Aides8Stack/GankSoft/issues/30) / [#31](https://github.com/Aides8Stack/GankSoft/issues/31) 同轮定向修复和验收，详见 [REVIEW-EVERY-SUBMISSION-SCHEDULED.md](./REVIEW-EVERY-SUBMISSION-SCHEDULED.md)。

## 2. 各批次的复用边界

| 批次 | 核心唯一职责 | 不能新增的平行实现 |
| --- | --- | --- |
| B1 卡片核心 | 统一卡片编辑会话、草稿显式持久化、正式发布事务和回执 | 不建立额外卡片草稿表/影子自动保存控制器 |
| B2 草稿箱/导航 | 一个草稿列表查询/删除合同、一种安全离开控制器 | 各子页面分别写一套“取消/自动保存/返回”逻辑 |
| B3 目录管理 | 复用 `workspace.catalog`/现有 CAS、卡片集内容包服务 | 文件夹导出、旧表完整ZIP假接口、独立“卡片集管理数据库” |
| B4 图谱和知识点选择 | **单个公共 KnowledgePicker API + 一份选中集合 + 一个当前激活的选择器弹窗** | 卡片关联/筛选学习各有独立图谱弹窗、把定位当选择、将创建节点混进选择 API |
| B5 Markdown 导出 | 复用图谱视图/ID 选择基础，单独实现逐节点导出规则 | 把逐节点导出规则强塞进通用选择弹窗、仅做假 UI 条件不改变服务端结果 |

## 3. 每批完成前的结构检查清单

- [ ] 新增或修改 API 是否列明**现有 API 为什么不够**？可复用的是否全部复用？
- [ ] 相同业务操作是否只有一套实现，还是复制到多个页面/组件？
- [ ] 新功能是否增加了不必要的全局状态、数据库表、IPC 通道、服务层或页面？若是，删减或给出具体必要性。
- [ ] 输入、确认、取消、失败/未知回执是否在**对应业务责任层**处理？是否做到“取消不写库、真正提交才落库”？
- [ ] 原有功能和快捷入口是否保留，还是拆模块时静默消失？旧生产路由是否仍可达？
- [ ] 是否只执行新功能的最小定向测试，同时核对重要复盘/数据一致性回归？
- [ ] 本次文件清单、公共 API 及调用点、调用层级是否写入交接文档？是否清楚区分设计原型、源码已接入、Electron测试通过、Windows实机验收？
- [ ] 如发现结构重复，是否优先**删除旧平行实现**而不是继续套一层适配器？删除前必须通过兼容测试。

## 4. 允许的复杂性与禁止的复杂性

**允许：** 为保证直接发布原子性/乐观锁、草稿删除幂等、单卡片集ZIP完整性、逐节点导出真实协议而增加必需且可验证的业务逻辑。

**禁止：** 为打开知识点选择器新增一个 Electron IPC；为每个页面创建独立知识图谱引擎/选择 Set；为了集中管理把 Markdown 导出规则和筛选选择强行合成通用巨型组件；为了“完善”界面新增宽侧栏、隐藏用户已依赖的功能或把成功提示当作真实事务回执。

**验收标准不是绝对代码行数减少，而是公共逻辑不重复、状态只有一个权威源、后端协议变更最少、现有功能不退化、数据链路可测试。**

本文件只记录约束与实施规划，不授权本轮立即修改生产代码。
