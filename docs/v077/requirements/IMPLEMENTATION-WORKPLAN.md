## 总体执行原则

1. **共五批，每次 Work 仅执行一个批次，每批最多三个检查点。** 各批完成后正常 commit/push 并远端独立核验 SHA、文件和必要证据；更新 `docs/development/RECOVERY-NEXT.md` 和本计划本批状态；立即结束，禁止自动进入下一批、强推、合并、发布或等待 CI。
2. **推荐 B1 → B2 → B3 → B4 → B5 串行推进。** `UnifiedWorkspace.vue`、图谱组件与 CSS 是共享热点，禁止多个 Work 在同一分支并发修改这些文件。可在单个 Work 内对独立测试使用多个 Worker 并行，严禁测试 Worker 共同修改生产源码。
3. 每轮只读取 `AGENTS.md`、`docs/development/STANDARDS.md`、`docs/development/RECOVERY-NEXT.md`、对应专题文件和直接受影响代码；不要重复读取整套历史报告、重跑已PASS的250个旧合同案例。
4. **先明确一致的数据/导航合同，再改 UI。** 禁止只改变按钮文案伪装落库成功；禁止修改 Schema606 而无清晰迁移/回滚保护；已有卡片、旧自动草稿、图片和 FSRS/ReviewEvent 必须保持完整。
5. 每次验收记录被测**生产 SHA、测试脚本 SHA、GUI操作、后台/SQLite断言、重启读回**，分别标记 PASS、FAIL、TEST_INFRA、BLOCKED、NOT_RUN。Linux Electron 不等于真 Windows 10/11。旧 235 PASS 等冻结结果不得冒充新版手动草稿合同的结果。
6. 新界面必须以仓库内 Vue 原型及 v3.7 原型为依据，**保留窄图标栏+卡片集列表**；主导航页无需强制返回按钮，所有二级/深层页面要能安全返回。
7. 生产工作阶段需用户把各批指令交给 Work 执行；本计划保存时**不启动任何开发**。Windows 便携测试 ZIP 通过已认可的 GitHub 手动构建方式从明确源 SHA 编译，不经过自动 RC 发布流程；未在 Windows 客户端实测前不得宣布最终通过。

## 交接格式与独立校验

每个 Work 结束时在报告中给出：
- 批次及3个检查点的 DONE/IN_PROGRESS/BLOCKED；
- 本批实际生产 SHA、测试脚本 SHA 与远端最终 HEAD 全40位 SHA；
- 新增/修复 CASE ID 和 PASS/FAIL/TEST_INFRA/BLOCKED/NOT_RUN；不改变旧冻结总账；
- 已知数据迁移/导出限制及 Windows 待验项；
- 本批真实修改文件、下一批入口、是否存在未保存提交；
- 明确“未合并、未发布、未等待 CI”。
