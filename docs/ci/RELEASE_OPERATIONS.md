# RC、Stable及恢复
RC：用户合并版本PR至受保护develop后自动运行。Work提交交接后结束。PR不打包。下载入口为仓库Releases的Pre-release；本轮没有现成新安装包。
队列：固定policy.adoptionBaseline扫描第一父链所有合并。A失败阻断后续，下一次develop push或所有者reconcile重扫、核对已发布资产摘要，补全部缺失SHA。单组cancel=false不代表FIFO，补偿扫描才保证漏发可恢复。不得修改adoptionBaseline掩盖失败。
受信任协调器以触发提交为上界，origin/develop包含该提交即可；允许后续合并到来，不把既合入版丢弃。发布资产使用本run精确命名artifact，不下载latest。
Draft重试：同SHA、同version、同一原始制品可以补传缺少文件，字节冲突或多余文件立即失败，保留Draft。重新构建产生不同run元数据/字节时，不覆盖旧Draft；在原run保留期内取回原制品，人工核验后从原发布Job恢复。缺失原制品则人工处置后发布新版本，不重用已撤回Tag。
Stable：先人工批准将正式SemVer源码及工作流推广main；由所有者在默认main运行stable-candidate，source_sha必须等于当时main HEAD。它完整测试/安全/Windows构建后只创建私有Draft，不发布Stable。
在Windows10和11分别下载同一正式Draft的portable.zip，运行tools/validation/windows-test.ps1，实际执行40项人工验收后逐项填写manualCases/manualSignoff；报告sourceSha、version、zipSha256、应用EXE SHA必须与同一正式包一致。不得伪造。
使用gh release upload vVERSION win10-actual.json win11-actual.json（不得--clobber）把两份真实报告附到该Draft。所有者再单独运行release-control的publish，输入完整source_sha及确认短语“publish vVERSION SHA”。它独立校验实际资产摘要/正式源码/40项同包报告和既有release:verify，才发布Stable。无须Work在场。
release-control query/rename/withdraw均所有者手动。rename确认“rename vVERSION”，允许标题/说明更正；withdraw确认“withdraw vVERSION SHA”只撤回Release，保留Tag作为不可重用墓碑。Immutable策略若拒绝变更应如实失败，不强制绕过。
未实现自动更新main、自动合并、自动公开、自动Stable。真实CI/Windows/发布故障演练必须在用户批准合并后进行；当前NOT_RUN。公开历史脚本只审计所有可访问Git refs，不能代替Actions日志/旧工件/版权/第三方App和个人资料人工审计。

## RC withdrawal and queue recovery (G2 change; not deployed)

`published()` remains deliberately strict: any retained Tag without a Release forbids publishing that version again. Queue history now uses `release-history.mjs`: `PENDING` / `DRAFT_RECOVERABLE` remain pending; a public RC must pass the existing complete remote artifact validation to be `PUBLISHED_VERIFIED`; only verified withdrawal evidence yields `WITHDRAWN_AUTHORIZED`. Every unexplained/conflicting state throws `BLOCKED` with a reason. History receipts include main SHA, modifying file commit, owner merge and Git blob identity; verified-plan/release artifacts preserve the remaining audit chain. No later RC skips quality, security, Windows package or artifact verification.

Authority is **not** a file from the candidate checkout, candidate `plan.json`, PR comment or release title. `withdrawal.mjs` reads `.github/release-withdrawals/v<canonical-rc.N>.json` from a pinned `main` SHA using GitHub API, verifies its blob hash, effective no-bypass protection and modifying owner-authored/owner-merged same-repository PR into main. A completed record must additionally match a successful exact-attempt owner `workflow_dispatch` Run of `.github/workflows/release-control.yml` on main, with execution SHA in main history and confirmation time inside that Run. Missing/failed/unknown API evidence blocks. Repository writers, approved owners, GitHub and protected main are the explicit trust root, as in the existing release design; granting an attacker owner/write credentials is outside this boundary. A JSON file or a successful unrelated candidate Run cannot grant authority.

Owner procedure **after separately approving deployment and G2 platform acceptance** (none executed by this Work):

1. Dispatch `release-control` on latest main, operation `withdraw-plan`, exact RC source SHA and a nonempty withdrawal reason. This only reads and verifies the original public RC, retained Tag, full artifacts and manifest. Its artifact contains an `AUTHORIZED` JSON snapshot: schema, repository, version, Tag, full source/lock SHA, original immutable Release ID/URL, manifest digest, reason, authorizer and authorization time.
2. Review the JSON and original Release evidence; merge only that authorization file via a **separate owner-controlled PR into protected main**. The source/Tag/Release/manifest fields must match the published RC; do not authorize a Draft or unexplained orphan. No script pushes main. Do not change an existing completed record or reuse a version.
3. Dispatch `withdraw` on the now-current main with confirmation `withdraw vVERSION FULL_SHA`. The script verifies the reviewed authorization, original public Release ID, source and manifest, then rechecks ID/Tag before deleting only that Release. It never deletes or changes the Tag. Effective main and develop release protections remain required. Existing concurrency groups serialize coordinator runs and manual operations; identity rechecks reject cross-group conflicts.
4. Download `withdrawal-record-RUN-ATTEMPT`, compare all authorization fields with the already-merged record, and review the successful Run, actor, workflow SHA, deletion evidence and retained Tag. Merge its `COMPLETED` JSON through another owner-controlled protected-main PR. It adds executor, Run/attempt/SHA, operation, `withdrawnAt`, and the exact original authorization commit/blob. The reader retrieves that historical blob, verifies all authorization fields are unchanged, checks its owner merge, and requires it to precede the execution SHA. The artifact is a transport copy retained 90 days, **not** the durable authority; main Git history is the authority. No automatic record merge or manual pr-trust authorization is performed by this code.
5. Reconcile develop normally. The historical item becomes `WITHDRAWN_AUTHORIZED`; its version/Tag remains consumed, and subsequent pending RCs traverse all original gates. Re-running the same withdrawn version is rejected by the unchanged publisher. The effective protection rules must already include strict pr-gate/pr-trust with Actions integration and no bypass actors; this Work does not configure them.

Interruption: before deletion, the original Draft/public state is preserved on failure. After deletion but before completion is merged, queue stays `BLOCKED: withdrawal completion receipt required`. Retry the same owner operation against the **existing reviewed authorization**: matching retained Tag plus absent Release yields `CONFIRM_AUTHORIZED_ABSENCE` without another DELETE. Its `withdrawnAt` is the time this Run confirmed the authorized withdrawn state (not a claim about an unknowable earlier API deletion timestamp). Normal `DELETE_RELEASE` records the first confirmation time after DELETE. The recovered receipt must pass the same successful-Run and owner-main-PR requirements before resuming queue. Missing prior authorization never permits orphan recovery. Once completed, repeated withdrawal returns the same recorded receipt without remote mutation. Run/API outage blocks until evidence is available. A reappearing Release, missing/moved Tag or Draft contradicting a completed receipt blocks.

Draft upload recovery remains the existing exact original-artifact transaction: a recoverable Draft is not a completed publication or withdrawal. Missing files may be uploaded; wrong source, changed bytes, extra assets or conflicting Tag fail closed. Concurrent different versions keep distinct tags/releases; same-version API conflicts and Tag race checks never overwrite history. Stable withdraw retains its explicit owner command, while Stable publication still requires both actual Win10/Win11 same-package signoffs and release:verify. These are isolated tests, not real RC/Stable authorization or platform acceptance.
