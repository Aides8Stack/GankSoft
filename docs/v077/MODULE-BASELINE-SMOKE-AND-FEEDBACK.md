## 1. 通用交互反馈合同（设计要求，不能当作已实现）

所有有写操作的功能至少检查以下五类反馈。

| 状态 | 用户必须看到的反馈 | 必须验证的业务行为 |
| --- | --- | --- |
| 待提交 / 未保存 | 明确表示有未提交变更；不可显示“已保存” | 页面可继续编辑，切页/退出不静默丢内容 |
| 正在处理 | 显示“保存中 / 发布中 / 导入中”等；重复提交受到保护 | 保持同一请求身份，避免双击产生重复数据 |
| 成功 | **收到可靠后端写入回执后**显示“已保存 / 发布成功 / 已恢复”；必要时提供可见的列表/详情入口 | UI 列表变化、只读落盘结果与重开一致；不以 toast 或按钮可点击判成功 |
| 失败、冲突、未知结果 | 具体、可操作的中文提示（例如必填项、保存失败、修订冲突、需要核对原请求）；保留已编辑内容与重试/核对方式 | 不吞错、不假装 clean、不自动重复未知结果事务；失败不损坏旧数据 |
| 取消、空结果 | 取消后明确保持原状；空列表/无可学习卡时有可理解空状态 | 不发生隐式写入；不把“没有草稿/没有卡片”表现为按钮没反应 |

**手动“保存草稿”**：按钮点击后必须可见保存中与已确认结果；即使自动保存已经完成，也应明确说明“草稿已保存”，并允许从草稿箱核验。**“发布卡片”**：必须说明发布中、成功或具体失败原因；若错题缺少正确答案等必填项，应指出字段，不得静默 return。成功后列表入口可达、内容与状态同步，不要求为了提示而重构整页 UI。

**报告状态**：只有 `PASS` / `FAIL` / `BLOCKED` / `NOT_RUN`；另记脚本是否 IMPLEMENTED，不能与 PASS 混淆。完整修复回归后才能把对应真实平台/源码 SHA 的 CASE 晋升为 PASS。

## 2. 每个功能组一条最小可用操作链（按正常使用优先，映射至原 CASE ID）

以下“预期反馈”是**必须测试的目标行为**，不是当前产品已通过的断言。完成时必须核验“从 UI 触发 → 观察状态 → 离开/返回 →（涉及持久化时）新 Electron 进程重开 → 只读数据核对”。无写操作的页面至少要查明内容/空态与来源。

| 模块（现有功能组） | 首轮 CASE ID | 最短用户操作链 | 应有可见反馈 | 最终核验点 |
| --- | --- | --- | --- | --- |
| 01 启动与窗口（ENV） | ENV-01、ENV-02 | 全新隔离库启动 → 首页 → 关闭 → 重开 | 首页或空库引导正确；异常明确提示 | 生产统一入口、Schema606、数据目录未串库 |
| 02 学习总览（HOME） | HOME-01、HOME-02 | 首页创建卡片集 → 进入集概览 | 创建成功、卡片集可进入；空态清晰 | 总卡数/待复盘数与只读结果一致 |
| 03 卡片集和目录（CAT） | CAT-02、CAT-04 | 新建卡片集 → 重命名 → 返回 → 重启 | 保存成功或明确重名/失败提示 | 同一 ID、名称和目录关系保持 |
| 04 新卡自动/手动草稿及发布（NEW） | NEW-01/02/03、**NEW-14、NEW-16、NEW-17** | 三种模式创建编辑 → 自动/鼠标保存 → 草稿箱打开 → 必填完整后鼠标发布 → 列表重开 | 每次写入有可信保存状态；缺项指明字段；发布成功可见 | 草稿可恢复，发布只新增一个正式卡 ID/版本，重启仍在 |

## 4. 单模块反馈记录格式（运行后填写，不在本设计预写 PASS）

每个模块/CASE 的执行摘要至少包含以下字段，汇总应写入已有 `docs/v077/E2E-RESULTS.json` 的可映射状态，并在本轮报告中按模块汇总：

```text
module: NEW
case_id: NEW-17
source_sha: <完整被测源码SHA>
environment: Linux Electron | Windows CI | Win10 Real | Win11 Real
scenario: <真实控件操作与最短复现步骤>
expected_ui: <预期保存中/成功/失败/空态提示>
actual_ui: <用户实际看到的反馈；如按钮无反应也要记录>
persisted: <只读查询/SQLite/文件哈希/重启校验结果>
status: PASS | FAIL | BLOCKED | NOT_RUN
severity_if_fail: P0 | P1 | P2
issue: <Issue编号或无>
fix_commit: <修复提交或无>
retest_source_sha: <复验被测SHA或无>
evidence: <本机原始路径/CI Artifact/精简截图日志哈希>
```

报告必须特别区分：
1. **UI 没反馈但数据已写成功**（交互反馈缺陷）。
2. **UI 提示成功但数据未写入**（虚假成功，P0 阻断）。
3. **UI/后端均失败且有清晰原因**（判断错误提示是否可行动；保留已编辑内容）。
4. **后台写入成功但列表未刷新**（同步显示缺陷，必须确认重开行为）。
5. **脚本/环境失败而业务尚未验证**（BLOCKED，不作为业务 FAIL）。

**每阶段保存要求：** 将真实执行的模块汇总与尚未完成项归档至 `docs/v077/`，最小更新 `docs/development/RECOVERY-NEXT.md`；禁止覆盖 `H1-REPORT.md` 中已经发生的历史事实。必要时更新 #16/#17/#18/#19/#21。每次 GitHub 保存完成均读取实际远端文件和完整 SHA 核验；没有真实运行不改 `E2E-RESULTS.json` 的 PASS 状态。
